国税庁の法人番号、国交省の位置参照情報と地価公示、厚労省や金融庁の許認可一覧——日本の官公庁は便利なオープンデータをたくさん公開してくれています。

ただ、いざ「企業の住所から緯度経度を引いて、最寄りの地価公示や許認可情報と SQL でサクッと JOIN したい」と思い立って手を動かすと、**想像以上に泥臭い前処理とライセンスの罠**にハマります。

この記事では、私が公的オープンデータを統合するパイプライン `jp-opendata-db` を作り、東京都（137万社）から全国47都道府県（583万社）まで SQLite / DuckDB / Parquet にまとめるまでに直面したリアルな壁と、その解決策をまとめました。

手元で試せる **2,000社分のサンプル SQLite（再構築コード付き）** も GitHub に置いています。

- GitHub（パイプライン＋2,000社サンプルDB）: https://github.com/terselogic/jp-opendata-db
- Hugging Face Datasets: https://huggingface.co/datasets/terselogic/jp-opendata-sample
- 全国47都道府県 ビルド済みアーカイブ案内: https://terselogic.com/datasets/jp-opendata/?utm_source=zenn&utm_medium=article

## ハマりポイント1：オープンデータなら何でも商用・二次配布できるわけではない

最初に一番時間を取られたのが技術ではなく**規約の読み込み**でした。

たとえば国土数値情報の「用途地域（A29）」や「洪水浸水想定区域（A31）」は GIS 分析で非常によく使われますが、詳細ページや FAQ を読み込むと「有償・商用製品への同梱不可（非商用制限）」が明記されています。また、国交省の宅建業者・建設業者検索システムは Web 検索画面があるだけで、公式の一括 CSV 配布がありません。

「作った DB をそのまま社内外のツールや商用サービスに組み込める状態」にしたかったため、一次規約をひとつずつ確認し、**出典表記を付ければ商用利用・二次配布まで問題ない 5 ソース**だけに絞りました。

| データソース | 主な用途 | 確認した利用条件 |
| :--- | :--- | :--- |
| 国税庁 法人番号公表サイト | 法人マスタ（13桁チェックデジット検証） | 公共データ利用規約（第1.0版） |
| 国交省 位置参照情報（街区 `24.0a`・町丁目 `18.0b`） | 住所→緯度経度ジオコーディング | 位置参照情報利用約款（Q20/Q21で有償二次配布可） |
| 国交省 国土数値情報 地価公示（`L01-25`） | 最寄り公示地価・距離計算 | 国土数値情報利用約款（L01商用可） |
| 厚労省 介護サービス情報公表システム | 事業所・法人番号欠損レコードの名寄せ | CC BY 4.0 / 厚生労働省利用規約 |
| 金融庁 免許・許可・登録業者一覧 | 金商・貸金・資金移動業者の名寄せ | 政府標準利用規約（第2.0版）準拠 |

## ハマりポイント2：文字コード・分割ZIP・表記揺れ・脚注ノイズ

データソースが決まってからも、いざパースすると日本の官公庁データならではの洗礼を受けます。

- **文字コードの混在**: UTF-8 と Shift-JIS（CP932）がソースごとにバラバラ
- **東京都だけ分割 ZIP**: 国税庁の法人番号データ（都道府県別）で、件数の多い東京都は `分割1` と `分割2` に分かれている
- **社名・住所の表記揺れ**: `㈱` / `（株）`、旧字体（`髙` / `﨑`）、漢数字の番地（`三丁目一番一号`）
- **許認可台帳の法人番号欠損と脚注**: Excel で配布されている一覧では法人番号が空欄だったり、社名の末尾に `株式会社○○※1` のような脚注記号がそのまま入っていたりする

### どうやって名寄せ精度を出したか

AI（LLM）でファジーに名寄せする案もありますが、数百万行を回すとコストも時間もかかる上、誤結合が起きると原因調査が大変です。そこで `src/jp_opendata/normalizer.py` と `permits.py` では、**完全に再現可能な決定論的 4 段階名寄せ**に割り切りました。

1. **国税庁のチェックデジット計算**で、元データ側の不正な 13 桁法人番号を先に弾く
2. **NFKC 正規化＋旧字体マッピング＋法人格統一＋漢数字→アラビア数字変換**で、住所の番地キーまで揃える
3. 以下の優先順位で段階的にマッチさせる
   - `tier1_explicit_corp_num` (1.00): 元データ記載の有効な法人番号
   - `tier2_exact_name_street` (0.95): 正規化商号＋市区町村＋番地キー一致
   - `tier3_core_name_municipality` (0.85): コア社名＋市区町村の一意一致
   - `tier4_core_name_prefecture` (0.70): コア社名＋都道府県の一意一致
4. **複数候補が出たら無理に繋がない**: 同名企業が同じ自治体に複数ある場合は `ambiguous` として保留し、誤結合を防ぐ

## 実際にビルドして計測した結果

まずは東京都データ（MVP）でパイプラインを検証し、その後、全国 47 都道府県へ拡張しました。

### 東京都 MVP の実測値
- **法人マスタ (`corporates`)**: 1,373,848 社
- **位置参照情報ジオコーディング成功**: 1,090,712 社（79.4%）
- **許認可・事業所 (`permits`)**: 4,625 件 → 法人番号への名寄せ一致 **4,319 件（93.4%）**
- **EDINET 財務リンク (`edinet_links`)**: 79 社（サンプル SQLite 内には 71 社を収録）
- **空間結合 (`spatial_profiles`)**: 2,000 社（DuckDB Spatial による最寄り地価公示単価・距離計算）

### 全国 47 都道府県フルビルドの実測値
- **法人マスタ (`corporates`)**: 5,830,372 社
- **空間結合 (`spatial_profiles`)**: 3,555,962 社（全国 L01-25 地価公示 25,563 地点と結合）
- **許認可・事業所 (`permits`)**: 97,581 件 → 法人番号一致 **96,115 件（98.5%）**

全国版まで広げると地方の許認可事業者ほど社名＋自治体の重複が減るため、名寄せ一致率は **98.5%** まで上がりました。

## 手元で 1 分で試してみる（サンプル SQLite + SQL）

GitHub リポジトリを clone すると、`sample/jp_opendata_sample.sqlite`（東京都 2,000 社分）がそのまま入っています。

```sql
SELECT c.corporate_number,
       c.company_name,
       e.sec_code,
       e.net_sales,
       s.nearest_land_price_yen_sqm,
       s.nearest_land_price_dist_m
FROM corporates c
JOIN edinet_links e ON c.corporate_number = e.corporate_number
JOIN spatial_profiles s ON c.corporate_number = s.corporate_number
ORDER BY e.net_sales DESC NULLS LAST
LIMIT 5;
```

この 1 本だけで、`ANAホールディングス` や `大東建託`、`長谷工コーポレーション` などの上場企業の売上高と、本社所在地から最寄りの地価公示単価・距離が横並びで取れます。

パイプライン自体を自分の環境で再ビルドしたい場合は、`uv` でそのまま動きます。

```bash
git clone https://github.com/terselogic/jp-opendata-db.git
cd jp-opendata-db
uv sync --all-extras
uv run pytest -v
uv run python scripts/build_mvp.py
```
